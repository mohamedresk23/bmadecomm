### Cross-story privacy and deployment

**F1 — Public media copies survive unpublishing. Instance: fix now (A1).** `src/lib/media/upload.ts:119` blocks generic publication only when an attachment owner is currently draft; a published catalog attachment is allowed through and copied to static `/uploads`. `src/modules/catalog/products/application/publication-service.ts:24` changes status/audit without revoking that copy. The runtime harness used real owner authentication and POST `/api/media/publish`, then POST unpublish. Both current/historical product slugs returned 404 while the temporary public copy remained readable. This violates draft-media privacy stated in `epic-4-context.md` Requirements and the E04-03 canonical constraints. The file was synthetic, in a uniquely created temporary storage root, and removed afterward. This is a cross-story defect newly reachable once publication exists; it is not a claim that public image delivery was authorized. **Prevention:** test every publication path against the full published-to-draft lifecycle, including generic media routes. Proposed fix must retain noncatalog logo/media compatibility and cover already created catalog public copies without silently destroying historical/private media.

**F2 — Gallery route trace omits image worker/native dependencies. Instance: fix now (A2).** `next.config.ts:5` includes worker/Sharp only for `/api/media/upload`; gallery upload also calls `processImage` through `gallery-service.ts:251`. Actual current build NFT inspection found gallery route: 0 worker entries, 0 Sharp entries; generic upload route: 1 worker, 111 Sharp entries. Evidence is the packaging JSON. A deployment assembled from the gallery route trace cannot be assumed to contain its dynamic worker. No deployment was performed and a complete packaged-gallery upload was not executed. **Prevention:** add a packaged-artifact verification for each new caller of spawned/native code, rather than relying on an earlier consumer's packaging test.

### Staff workflow integration

**F3 — Published gallery offers changes the server refuses. Instance: fix now (A3).** `product-manager.tsx:302` passes product ID/variants/busy state but no persisted publication status. `product-gallery.tsx:518` and `:545` enable save/upload according to dirty/loading state; `gallery-service.ts:469` and `:666` enforce draft-only updates/removal. Local gallery dirtiness also feeds the publication dirty guard at `product-manager.tsx:297`, disabling unpublish until edits are discarded. Existing UI controls therefore invite an operation that cannot succeed for a published product. **Prevention:** include a published-product gallery interaction in the composed editor test, not just separate gallery and publication tests.

- **D1:** Published product PUT can clear description/zero price while remaining published. Reproduced with HTTP PUT, readiness=false and public GET=200. - **D2:** Slug redirects are created only when status is currently published (`slug-service.ts:198-201`; contract section 2.1).
